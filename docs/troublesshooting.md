# Troubleshooting

This document records issues encountered during the deployment of the self-hosted RustDesk environment and the steps used to diagnose and solve them.

## RustDesk Key Mismatch

### Symptom

A RustDesk client could reach the self-hosted server but returned a key mismatch error when attempting to establish a connection.

### Cause

The client was configured with a public key that did not match the key generated by the current `hbbs` server.

RustDesk Server generates a key pair during initialization:

```text
id_ed25519
id_ed25519.pub
```

The private key remains on the server, while clients must use the corresponding public key.

### Verification

The server public key was checked with:

```bash
cat /opt/rustdesk/data/id_ed25519.pub
```

### Solution

The RustDesk configuration on both clients was updated to use the same public key generated by the self-hosted `hbbs` server.

After correcting the key, both clients successfully registered and established a remote connection.

## Docker Compose Configuration File Not Found

### Symptom

Running:

```bash
docker compose ps
```

returned:

```text
no configuration file provided: not found
```

### Cause

The command was executed from the user's home directory instead of the RustDesk project directory.

Docker Compose searches for a `compose.yml` or compatible Compose file in the current working directory.

The RustDesk Compose file is stored in:

```text
/opt/rustdesk/compose.yml
```

### Solution

Change to the correct directory:

```bash
cd /opt/rustdesk
docker compose ps
```

Alternatively, specify the Compose file explicitly:

```bash
docker compose -f /opt/rustdesk/compose.yml ps
```

## No-IP DUC Installed but Not Running

### Symptom

Checking the No-IP service returned:

```text
Loaded: loaded
Active: inactive (dead)
```

### Cause

The No-IP Dynamic Update Client was installed, but the service had not been configured and enabled for automatic startup.

The configuration file:

```text
/etc/default/noip-duc
```

was also missing.

### Solution

The No-IP DUC configuration file was created locally on the server.

The service was then enabled and started using:

```bash
sudo systemctl enable --now noip-duc
```

Its status was verified with:

```bash
sudo systemctl status noip-duc
```

The expected state is:

```text
Active: active (running)
```

The service was also tested after a full Ubuntu reboot to confirm automatic startup.

## Verifying External RustDesk Connections

### Goal

Confirm that an external RustDesk client was actually reaching the self-hosted server through the Internet.

### Verification

Active RustDesk TCP connections were inspected using:

```bash
sudo ss -tnp | grep -E '21115|21116|21117'
```

An established connection was observed on TCP port `21116`:

```text
ESTAB ... 192.168.1.202:21116 ... EXTERNAL_IP:PORT ... hbbs
```

This confirmed that an external client was communicating directly with the self-hosted `hbbs` service.

### Interpretation

Port `21116` is associated with the RustDesk `hbbs` service and is involved in connection establishment and signaling.

A connection on port `21117` associated with `hbbr` would indicate relay traffic.

## Monitoring RustDesk Logs

RustDesk server logs can be inspected directly through Docker.

### hbbs logs

```bash
docker logs -f --timestamps hbbs
```

### hbbr logs

```bash
docker logs -f --timestamps hbbr
```

To inspect recent logs without following them continuously:

```bash
docker logs --tail 50 hbbs
```

```bash
docker logs --tail 50 hbbr
```

Logs are useful for identifying:

* client registration
* connection attempts
* relay activity
* startup problems
* runtime errors

## Verifying Listening Ports

To confirm which RustDesk ports are listening on the Ubuntu Server:

```bash
sudo ss -tulpn | grep 211
```

Expected services include:

```text
21115/TCP
21116/TCP
21116/UDP
21117/TCP
```

If a required port is not listening, the related RustDesk service or container should be checked.

## Checking Docker Containers

To verify the current RustDesk containers:

```bash
cd /opt/rustdesk
docker compose ps
```

Expected containers:

```text
hbbs
hbbr
```

Both should normally report a running state.

Additional Docker information can be obtained using:

```bash
docker ps
```

and:

```bash
docker logs hbbs
docker logs hbbr
```

---

## Checking the Host Firewall

UFW status can be inspected with:

```bash
sudo ufw status numbered
```

The RustDesk deployment requires:

```text
21115/TCP
21116/TCP
21116/UDP
21117/TCP
```

SSH access should remain restricted to the internal LAN.

## DNS Troubleshooting

The Dynamic DNS hostname can be validated using:

```bash
nslookup rustdesk.example.ddns.net
```

The returned IPv4 address should match the current public IPv4 address of the Internet connection.

If the hostname resolves to an outdated address, the No-IP DUC service should be checked:

```bash
sudo systemctl status noip-duc
```

Logs can be inspected with:

```bash
sudo journalctl -u noip-duc -n 30 --no-pager
```

## Basic Troubleshooting Workflow

When the RustDesk service is not working as expected, the following sequence can be used:

```text
1. Check Docker containers
        |
        v
2. Check RustDesk logs
        |
        v
3. Verify listening ports
        |
        v
4. Check UFW rules
        |
        v
5. Verify DNS resolution
        |
        v
6. Verify NAT / Port Forwarding
        |
        v
7. Check active TCP connections
```

Useful commands:

```bash
cd /opt/rustdesk
docker compose ps

docker logs --tail 50 hbbs
docker logs --tail 50 hbbr

sudo ss -tulpn | grep 211

sudo ufw status numbered

nslookup rustdesk.example.ddns.net

sudo ss -tnp | grep -E '21115|21116|21117'
```

This workflow helps isolate whether a failure is related to the application, Docker, Linux networking, firewall rules, DNS, or external connectivity.

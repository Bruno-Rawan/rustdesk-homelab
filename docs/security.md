# Security Considerations

This document describes the main security decisions applied to the self-hosted RustDesk environment.

## Dedicated Server

The RustDesk Server runs inside a dedicated Ubuntu Server virtual machine hosted on Proxmox VE.

This isolates the remote access service from other homelab workloads and makes maintenance, troubleshooting, and access control easier.

## Host Firewall

UFW is enabled on the Ubuntu Server.

Only the ports required by the RustDesk Server OSS deployment are exposed:

| Port  | Protocol | Purpose                     |
| ----- | -------- | --------------------------- |
| 21115 | TCP      | NAT type test               |
| 21116 | TCP      | Connection / hole punching  |
| 21116 | UDP      | ID registration / heartbeat |
| 21117 | TCP      | Relay traffic               |

Unused RustDesk Web Client ports are not exposed.

This follows the principle of least privilege: only services required by the application should be reachable.

## SSH Access

SSH is used for server administration.

SSH access is restricted to the internal LAN:

```text
192.168.1.0/24 -> TCP/22
```

Port `22/TCP` is not forwarded through the Internet router.

Remote administration of the Ubuntu Server is therefore not directly exposed to the public Internet.

## RustDesk Cryptographic Keys

During the first startup, the RustDesk Server generates a key pair.

```text
id_ed25519
id_ed25519.pub
```

### Private Key

```text
id_ed25519
```

The private key must remain stored only on the RustDesk Server.

It must never be:

* committed to Git
* uploaded to GitHub
* shared with clients
* included in screenshots
* stored in public documentation

### Public Key

```text
id_ed25519.pub
```

The public key is used by RustDesk clients to verify the self-hosted server.

Clients must use the public key generated by the current `hbbs` server.

## Persistent Data

RustDesk data is stored under:

```text
/opt/rustdesk/data
```

The Docker Compose deployment maps this directory into the RustDesk containers.

```yaml
volumes:
  - ./data:/root
```

This keeps server configuration and cryptographic material outside the container lifecycle.

The `data/` directory is excluded from Git using `.gitignore`.

## Dynamic DNS Credentials

No-IP Dynamic DNS is used because the Internet connection uses a dynamic public IPv4 address.

The No-IP Dynamic Update Client requires authentication credentials.

These credentials are stored locally on the server and are intentionally excluded from the repository.

The repository must never contain:

```text
DDNS username
DDNS password
DDNS keys
API tokens
```

## Sensitive Information

The following information is intentionally excluded from the public repository:

* Public IPv4 address
* Real DDNS hostname
* RustDesk private key
* DDNS credentials
* Passwords
* API tokens
* Authentication secrets

Example or placeholder values are used in public documentation instead.

## Git Protection

The repository includes a `.gitignore` file to reduce the risk of committing sensitive data.

Examples:

```gitignore
data/

id_ed25519
*.key
*.pem

.env
.env.*

*credentials*
*secret*

*.log
```

Important:

`.gitignore` only prevents untracked files from being added automatically.

If a sensitive file has already been committed, adding it to `.gitignore` does not remove it from Git history.

## Container Security

The RustDesk services run inside Docker containers.

The containers use:

```yaml
restart: unless-stopped
```

This allows the services to recover automatically after a reboot while still allowing intentional administrative shutdown.

The deployment uses host networking:

```yaml
network_mode: "host"
```

Because host networking gives the containers direct access to the host network stack, the host firewall is an important part of the security model.

## Router Exposure

Only RustDesk service ports are forwarded from the public Internet to the RustDesk Server.

```text
21115/TCP
21116/TCP
21116/UDP
21117/TCP
```

Management services such as SSH are intentionally not forwarded.

## Security Principles Applied

The deployment follows these basic principles:

* Least privilege
* Minimal exposed attack surface
* Separation of application and management access
* No secrets stored in Git
* Persistent cryptographic data protected outside containers
* Dedicated service VM
* Host firewall enabled
* Management access restricted to the LAN

## Future Improvements

Possible security improvements for future versions include:

* SSH key authentication
* Disable SSH password authentication
* Fail2ban
* Dedicated management VPN
* Log monitoring
* Automated security updates
* Container image version pinning
* Regular backup of RustDesk server keys and configuration
